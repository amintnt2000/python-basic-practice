# 🏦⚡ سیستم بانکی با FastAPI (Banking REST API)

نسخه تکامل‌یافته پروژه سیستم بانکی OOP، این‌بار به‌صورت یک REST API کامل با FastAPI. منطق اصلی (کلاس‌های `Account` و `BankLogic`) از پروژه OOP اولیه حفظ شده و یک لایه API روی آن قرار گرفته است.

## 🎯 هدف پروژه

نشان دادن نحوه ترکیب برنامه‌نویسی شی‌گرا (OOP) با یک فریم‌ورک وب (FastAPI) — الگویی که در پروژه‌های واقعی نرم‌افزاری بسیار رایج است: منطق تجاری (business logic) در کلاس‌ها نگه داشته می‌شود و FastAPI فقط به‌عنوان لایه ورودی/خروجی (HTTP) عمل می‌کند.

## 🏗️ ساختار پروژه

### لایه منطق (بدون تغییر نسبت به نسخه OOP)

- `Account`: مدیریت موجودی، واریز، برداشت، با validation و Custom Exceptions
- `BankLogic`: مدیریت مجموعه حساب‌ها، ساخت حساب جدید، جستجو بر اساس شماره حساب
- `InsufficientFundsError` و `InvalidAmountError`: خطاهای اختصاصی برای موجودی ناکافی و مقدار نامعتبر

### لایه API (جدید)

| متد | آدرس | توضیح |
|---|---|---|
| `POST` | `/account` | ساخت حساب جدید |
| `GET` | `/account/{account_number}` | دریافت جزئیات یک حساب |
| `POST` | `/account/{account_number}/deposit` | واریز به یک حساب |
| `POST` | `/account/{account_number}/withdraw` | برداشت از یک حساب |
| `POST` | `/transfer` | انتقال وجه بین دو حساب |

## 🚀 نحوه اجرا

```bash
pip install fastapi uvicorn
uvicorn main:app --reload
```

مستندات تعاملی: `http://127.0.0.1:8000/docs`

## 📋 مثال استفاده

**ساخت حساب:**
```
POST /account
Body: {"owner_name": "Ali"}
```

**واریز:**
```
POST /account/1/deposit
Body: {"amount": 1000}
```

**انتقال وجه:**
```
POST /transfer
Body: {"from_account": 1, "to_account": 2, "amount": 300}
```

## 🧠 نکات آموزشی کلیدی

1. **تبدیل Custom Exceptions به HTTPException:** خطاهای اختصاصی کلاس `Account` (مثل `InsufficientFundsError`) در لایه route با `try/except` گرفته شده و به `HTTPException` با کد HTTP مناسب (مثلاً ۴۰۰ یا ۴۰۴) تبدیل می‌شوند — چون کاربر نهایی API نمی‌تواند مستقیماً با کلاس‌های Exception پایتون کار کند، فقط با کدهای استاندارد HTTP.

2. **جداسازی مسئولیت‌ها:** کلاس‌های `Account` و `BankLogic` هیچ وابستگی به FastAPI ندارند و می‌توانند مستقل از آن هم استفاده شوند (دقیقاً مثل نسخه اصلی OOP). این جداسازی باعث می‌شود منطق تجاری قابل تست و استفاده مجدد باشد.

3. **چند Pydantic Model برای سناریوهای مختلف:** به‌جای یک مدل عمومی، برای هر نوع عملیات یک مدل جدا تعریف شده (`CreateAccountRequest`, `AmountRequest`, `TransferRequest`) که هرکدام فقط فیلدهای مرتبط با همان عملیات را دارند.

4. **مدیریت عملیات چند-حسابی:** در `/transfer`، به‌جای فراخوانی متد `transfer` کلاس (که در نسخه OOP وجود داشت)، منطق مستقیماً در route با فراخوانی `withdraw` و `deposit` روی دو آبجکت جداگانه پیاده‌سازی شده است.
